# Передача сайта Royal Snow: что нужно от заказчика и что получает заказчик

Домен, сервер и аккаунты оформляются на заказчика и ведутся его людьми (ТЗ п. 12). Этот документ — единый список: что подготовить, как развернуть, что и кому передаётся, что решить до запуска.

## 1. Что нужно подготовить заказчику (чек-лист)

### 1.1. Домен
- Домен зарегистрирован **на заказчика** (аккаунт у регистратора на его почту/организацию).
- Доступ к управлению DNS (у регистратора или в Cloudflare/Яндекс 360 и т. п.).
- Записи: **A** `домен` → IPv4 сервера; при желании **A** `www` → тот же IP (редирект `www` → основной домен в сайте не настроен, это отдельная мелкая доработка).
- Если DNS через Cloudflare: на время выпуска сертификата режим **«DNS only»** (серое облако), иначе HTTPS может не выпуститься.

### 1.2. Сервер
- **VPS в России** (персональные данные граждан РФ хранятся в РФ, 152-ФЗ): Ubuntu 22.04 или 24.04.
- Минимум **2 vCPU, 2 ГБ RAM, 40 ГБ SSD**; рекомендуем **2 vCPU, 4 ГБ RAM, 60 ГБ SSD**. При 2 ГБ RAM добавьте swap на время сборки.
- **Статический публичный IPv4**, открытые порты **80, 443** (сайт и HTTPS) и **22** (SSH, лучше с ограничением по IP). Порт базы наружу не открывается.
- Доступ технического специалиста: SSH по ключу, пользователь с `sudo`.
- Место для резервных копий вне сервера (другой диск, облако, второй сервер).

### 1.3. Telegram (уведомления и бот-посредник)
- Бот создаёт **человек заказчика** у @BotFather (владелец бота = заказчик, токен не пересылается).
- Группа менеджеров с включёнными **«Темами»**, бот — администратор с правом «Управление темами»; id группы (`-100…`).
- Для режима «бот-посредник» — аккаунт **Cloudflare** (бесплатный, без карты) на заказчика. Пошагово: `bot-cloudflare/README.md`.

### 1.4. Контакты и тексты
- Основной телефон уже указан: +7 (991) 959-89-85. Нужны: дополнительные номера (если есть), **e-mail**, адрес (если показывать), ссылки на **Telegram и WhatsApp** компании.
- Названия услуг и описания: сверить тексты на сайте. Цены и гарантии на сайте **не публикуются**; всё, что не подтверждено заказчиком, не добавлять.

### 1.5. Материалы
- **Логотип**: SVG и PNG на прозрачном фоне (светлый и тёмный варианты). Сейчас временный знак (снежинка под короной).
- **Фотографии выполненных работ** (только реальные, с правом публикации) и **подтверждённые отзывы**.
- Видео/фон первого экрана: сейчас сгенерировано нейросетью (Hailuo AI); проверить условия сервиса и права, при необходимости заменить реальным (файлы `public/hero/`).

### 1.6. Юридические документы (до публикации формы)
- Реквизиты оператора персональных данных (юрлицо/ИП).
- **Политика обработки ПДн** и **Согласие на обработку ПДн**: на сайте шаблоны (`/politika-konfidencialnosti`, `/soglasie`), юрист должен утвердить финальные тексты.
- Вопросы юристу: уведомление Роскомнадзора об обработке ПДн; передача данных в Telegram и хранение идентификаторов в Cloudflare (за рубежом) при использовании бота; политика cookie и Яндекс.Метрика.

### 1.7. Аналитика
- Счётчик **Яндекс.Метрики** (номер) — вносится в «Настройки сайта». Цели (JavaScript-события): `lead_submit`, `phone_click`, `messenger_click` создаются в интерфейсе Метрики.

### 1.8. Организационное
- Ответственные: кто получает заявки, кто администратор сайта, кто отвечает за сервер/домен.
- **Условия гарантии и поддержки** (ТЗ п. 13): срок гарантии, что входит в поддержку, стоимость, сроки реакции. В этом документе они не определены, их нужно согласовать отдельно.

## 2. Что получает заказчик

- Исходный код (репозиторий) и дизайн-материалы; документация (`docs/`, `bot-cloudflare/README.md`).
- Рабочий сайт с формой заявки, базой данных и админкой (заявки, статусы, заметки, редактирование услуг, текстов, фото, контактов).
- Telegram-уведомления о заявках; бот-посредник (по желанию, после настройки Cloudflare).
- Скрипты и инструкции: развёртывание (`docs/DEPLOY.md`), резервные копии (`docs/BACKUP.md`, `scripts/backup.sh`), руководство администратора (`docs/ADMIN_GUIDE.md`).
- **Репозиторий** сейчас находится в аккаунте разработчика. Передача: либо добавить заказчика владельцем, либо GitHub → Settings → **Transfer ownership**; после передачи разработчик не должен сохранять доступ без согласования.
- **Vercel-превью** (`maxkrest.vercel.app`) — только для показа, на боевой запуск не влияет; после передачи отключается.

## 3. Развёртывание (для технического специалиста)

```bash
# 1. Docker (Ubuntu)
curl -fsSL https://get.docker.com | sh

# 2. Код
git clone <адрес репозитория> /opt/royal-snow && cd /opt/royal-snow

# 3. Настройки
cp .env.example .env
# сгенерируйте секреты и впишите значения в .env:
openssl rand -hex 32   # для AUTH_SECRET
openssl rand -hex 32   # для CRON_SECRET
openssl rand -hex 16   # для DB_PASSWORD
```
Обязательные значения в `.env`: `DB_PASSWORD`, `SITE_URL` (`https://домен`, без слэша в конце), `SITE_DOMAIN` (`домен`), `AUTH_SECRET`, `CRON_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` (не короче 10 символов). По желанию: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `BOT_USERNAME`, `LEAD_PULL_SECRET`, `LEAD_NOTIFY_DIRECT`.

```bash
# 4. Запуск (миграции, начальное наполнение и первый администратор — автоматически)
docker compose up -d --build

# 5. Проверка
docker compose ps
curl https://домен/api/health      # {"ok":true,...}
```
Дальше:
1. DNS уже должен указывать на сервер, иначе сертификат не выпустится (Caddy делает это сам).
2. Войти на `https://домен/admin/login`, затем **удалить `ADMIN_PASSWORD` из `.env`** (иначе при каждом перезапуске пароль сбрасывается на него).
3. «Настройки сайта»: название, логотип, телефоны, e-mail, мессенджеры, номер Метрики, chat id для Telegram.
4. Отправить тестовую заявку: она появляется в админке и в Telegram-группе.

Логи: `docker compose logs -f app`. Обновление: `git pull && docker compose up -d --build`. Остановка/запуск: `docker compose down` / `up -d` (данные хранятся в томах `pgdata` и `uploads`, `down` их не удаляет).

## 4. Резервные копии
- `./scripts/backup.sh` делает дамп базы и архив загруженных файлов в `./backups` (хранит 14 последних).
- Cron на сервере, например каждый день в 03:00: `0 3 * * * cd /opt/royal-snow && ./scripts/backup.sh >> backups/backup.log 2>&1`.
- **Копии нужно выгружать за пределы сервера** (иначе при потере сервера они пропадут).
- Восстановление: `docs/BACKUP.md`. Один раз проверьте восстановление на тестовом сервере.

## 5. Безопасность (минимум)
- SSH только по ключу, пароль root отключён; фаервол пропускает только 22/80/443.
- Файл `.env` не попадает в репозиторий и никому не пересылается; секреты хранятся у ответственного лица.
- Пароль администратора длинный и уникальный; смена пароля: задать `ADMIN_EMAIL` и новый `ADMIN_PASSWORD`, перезапустить `app`, затем снова убрать пароль из `.env`.
- Регулярно обновлять ОС (`unattended-upgrades`) и образы (`git pull && docker compose up -d --build`).

## 6. Таблица передачи доступов

| Что | На кого оформлено | Кто получает доступ |
|---|---|---|
| Домен и DNS | заказчик | техспециалист заказчика |
| Сервер (VPS) | заказчик | техспециалист заказчика (SSH) |
| Репозиторий с кодом | заказчик (после передачи) | техспециалист заказчика |
| Админка сайта | учётная запись на e-mail заказчика | ответственный менеджер/владелец |
| База данных | пароль в `.env` на сервере | техспециалист заказчика |
| Telegram-бот (@BotFather) | аккаунт заказчика | владелец бота |
| Telegram-группа менеджеров | заказчик | менеджеры |
| Cloudflare (Worker бота) | аккаунт заказчика | техспециалист заказчика |
| Яндекс.Метрика | аккаунт заказчика | маркетолог/владелец |

Принцип: все аккаунты и доступы остаются у заказчика, исполнитель их не удерживает (ТЗ п. 12). Передача проекту другому исполнителю — репозиторий, `.env` (через защищённый канал), это руководство.

## 7. Приёмка (ТЗ п. 15)
Проверить на боевом домене: открытие на компьютере и смартфоне; описание каждой услуги; форма показывает только нужные поля услуги; проверка телефона и обязательных полей; загрузка нескольких фото; подтверждение с номером заявки; заявка в базе и в админке; Telegram-уведомление (и сохранение заявки при сбое Telegram); смена статуса и заметки; редактирование услуг, текстов, фото, контактов; работа ссылок телефона и мессенджеров; защита админки; резервное копирование; передача доступов, кода и инструкции.

## 8. Что не проверено разработчиком и требует проверки на месте
- Сборка Docker-образа и `docker compose up` на реальном сервере, `scripts/backup.sh` и восстановление (в среде разработки нет Docker).
- Работа бота в реальном Telegram и Cloudflare (проверено на моках и на тестовом сайте).
- Выпуск HTTPS-сертификата на боевом домене.
- Тексты политики и согласия (шаблоны, нужен юрист).

## 9. Вопросы, которые нужно решить до запуска
1. Провайдер VPS и кто его оплачивает.
2. Юрлицо/ИП оператора и реквизиты для документов.
3. Нужен ли бот-посредник или достаточно прямых уведомлений в группу.
4. Условия гарантии и поддержки, сроки реакции, стоимость.
5. Периодичность и место хранения резервных копий.
6. Нужен ли отдельный тестовый сервер для проверки обновлений.
7. Редирект с `www` и дополнительные домены.
